## 1. Краткий вывод

Продукт в целом держится: собственные подсистемы (push-реле, capability, подписи релизов, CI-гейты, схема подписи истории NGC, хранение ключей на трёх платформах) выдержали состязательную проверку — из 32 кандидатов 20 отклонены, в том числе все, что относились к невыпускаемой линии `khandaq-android/` (aTox) и к выведенной из эксплуатации `infra/bootstrap/`. Основной остаточный риск — не в коде Khandaq, а в вендоренном C-toxcore: в тракте RTP звонков 1:1 есть два дефекта памяти (порча кучи и удалённое падение), достижимых от уже принятого контакта во время звонка, причём один из них живёт только в iOS-копии, где отсутствует проверка границ, имеющаяся в desktop-копии. Отдельно: релизный конвейер сейчас сломан в двух местах — следующий тег не соберётся (проверка предка на shallow-клоне), а следующая пересборка десктопа не выложится (отказ подписи пересобранного артефакта); оба дефекта внесены свежей ремедиацией и ни разу не исполнялись. Третья группа — гейты и защиты, которые формально есть, но не могут сработать: проверка FCM-кредов грепает не то поле, а `deploy-site.sh --rollback` на несколько секунд публикует копии nginx-конфигов в веб-корне.

## 3. Находки

### RR3-01 (high) — RTP: отказ пакета после открытия слота ломает учёт `next_free_entry`

**Что не так.**
`khandaq-desktop/buildscripts/toxcore/toxav/rtp.c`, функция `fill_data_into_slot` (266-346):
- строка 276 — ветка «новый слот» выбирается по `slot->received_len == 0`;
- строки 296-309 — `calloc`, `slot->buf = msg`, `slot->received_len = 0`, `assert(next_free_entry < 3)` и `++wkbl->next_free_entry`;
- строка 322 — проверка `header->data_length_full - header->offset_full < incoming_data_length` возвращает `false` уже ПОСЛЕ инкремента.

Слот остаётся с `buf != nullptr` и `received_len == 0`, счётчик увеличен. `get_slot` (129-206) в мультипарт-ветке (143-155) отдаёт тот же слот по совпадению `sequnum`+`timestamp`, и следующий пакет снова уходит в «новую» ветку: утечка предыдущего `msg` и ещё один инкремент.

Асёрты в бою выключены: desktop собирается `CMAKE_BUILD_TYPE=Release`, Android — с явным `-DNDEBUG` (`khandaq-android-trifa/circle_scripts/deps.sh:537`), тот же ref `zoff99/c-toxcore @2e7a0675` без патча rtp.c. `next_free_entry` — `int8_t`, `work_buffer[3]` (`rtp.h:219-220`, `USED_RTP_WORKBUFFER_COUNT` = 3, `rtp.h:56`). `handle_video_packet` (415-445) отбрасывает только `-1`/`-2`, а параметр `slot_id` объявлен `const uint8_t`. iOS-копия идентична: `rtp.m:265-346` (ветка 277, инкремент 309); правка KHANDAQ F-01 стоит после инкремента и счётчика не касается.

Важное уточнение к первоначальной формулировке: отвергнутый пакет — не единственный путь. Пакет с нулевой полезной нагрузкой (`length == RTP_HEADER_SIZE + 1`) проходит все проверки, `memcpy` копирует 0 байт, `received_len` остаётся 0 — и следующий пакет с тем же `sequnum` снова открывает слот. Поэтому перенос проверок вверх дефект не закрывает.

**Сценарий отказа.** Друг, с которым принят обычный 1:1 звонок (audio- и video-RTP-сессии создаются безусловно в `call_prepare_transmission`, `toxav.c:2621+`), шлёт lossy-пакеты `RTP_TYPE_VIDEO` с флагом `RTP_LARGE_FRAME`, одинаковыми `sequnum`/`timestamp` и `data_length_full - offset_full < payload`:
- 2 пакета → `next_free_entry == 2`, при этом `work_buffer[1].buf == nullptr`;
- 3-й пакет с ДРУГИМ `sequnum` → `get_slot` разыменовывает `slot->buf->header.sequnum` на NULL → **SIGSEGV, клиент падает во время звонка** (воспроизведено на выдернутых функциях, код выхода 139);
- если счётчик дорос до 4 и звонок завершается — `rtp_kill` (1107) в цикле `for (int8_t i = 0; i < next_free_entry; ++i)` читает указатель за концом 56-байтной аллокации `RTPWorkBufferList` и передаёт его в `free()` (ASan: heap-buffer-overflow READ of size 8);
- 129 пакетов → `int8_t` переполняется в −128, `get_slot` возвращает −128, `slot_id` становится 128 → запись примерно на 2000 байт за массив.
Плюс на каждый такой пакет утекает `sizeof(RTPMessage) + data_length_full + 64`.

**Как чинить (по шагам).**
1. В `fill_data_into_slot` заменить условие ветки на состояние буфера, а не на счётчик принятых байт: `if (slot->buf == nullptr) { ... }`. Это единственная правка, закрывающая и вариант с нулевой нагрузкой.
2. Все проверки корректности пакета (`data_length_full > MAX_RTP_FRAME_SIZE`, `data_length_full - offset_full < incoming_data_length`) перенести в начало функции, до аллокации.
3. Заменить `assert(wkbl->next_free_entry < USED_RTP_WORKBUFFER_COUNT)` (308) на реальную проверку: `if (wkbl->next_free_entry >= USED_RTP_WORKBUFFER_COUNT) { free(msg); return false; }`.
4. В `handle_video_packet` после каждого вызова `get_slot` (417 и 441) отбрасывать любой `slot_id` вне `0..USED_RTP_WORKBUFFER_COUNT-1`, а не только `-1`/`-2`.
5. Внести идентичную правку в `khandaq-ios/local_pod_repo/toxcore/toxcore/toxav/rtp.m` (ветка 277, инкремент 309, проверка после).
6. **Правку в дереве недостаточно закоммитить.** Docker-образы десктопа (`buildscripts/docker/Dockerfile.debian:61-64`, `Dockerfile.khandaq_ubuntu2404:76-79`, `Dockerfile.windows_builder`) копируют в `/build` только скрипты, поэтому `download_toxcore.sh` клонирует апстрим заново. Оформить правку как applier-скрипт по образцу `khandaq-android-trifa/patches/apply_khandaq_toxav_ngc_chroma.py` (точечная подстановка + `exit 1`, если исходный текст не найден) и вызвать его: (а) в `buildscripts/build_toxcore.sh`/`build_toxcore_linux.sh` сразу после загрузки; (б) в `khandaq-android-trifa/circle_scripts/deps.sh` во всех четырёх ABI-блоках (рядом со строками 517-523, 1111-1117, 1706-1712, 2147-2153) с `|| exit 1`.
7. `khandaq-desktop/buildscripts/toxcore/amalgamation/toxcore_amalgamation.c` править не обязательно — ни один путь сборки её не компилирует (потребители только собственный `amalgamation/Makefile` и тесты). Если правите — только ради согласованности.

**Как проверить.** Расширить `scripts/rtp_reassembly_harness.c.in` тремя кейсами и включить их в `scripts/check-ios-rtp-reassembly.py`: (1) первый пакет кадра отвергнут — `next_free_entry` обязан остаться 0; (2) три пакета «повторное открытие слота» — нет разыменования NULL; (3) пакет с нулевой полезной нагрузкой — счётчик не растёт. Отдельно: после сборки APK убедиться, что applier сработал (`strings`/дизассемблер по новой проверке границ), иначе он молча пропущен, как это уже бывало.

**Объём.** Средний: сама правка — десятки строк, основная работа в appliers и в четырёх точках вызова + тесты.

### RR3-02 (high) — iOS `rtp.m`: в legacy-ветке RTP нет проверок границ, которые есть в desktop-копии

**Что не так.** Ровно случай «правка есть в одной копии и нет в другой».
Desktop (`rtp.c`): в `NEW_MULTIPARTED` стоит `if (header.data_length_lower - header.offset_lower < (int)(length - RTP_HEADER_SIZE)) return;` (939), и третье условие в ветке дозаполнения (897).
iOS (`rtp.m`): обеих проверок нет.
- `rtp.m:628` — `new_message(&header, header.data_length_lower, data + RTP_HEADER_SIZE, length - RTP_HEADER_SIZE)`: `allocate_len` = 16-битное поле заголовка, полностью подконтрольное отправителю.
- `rtp.m:56-68` — `new_message` делает `assert(allocate_len >= data_length)`, затем `calloc(sizeof(RTPMessage) + allocate_len)` и `memcpy(msg->data, data, msg->len)`.
- `rtp.m:580-581` — проверяются только `data_length_lower - mp->len < chunk` и `data_length_lower <= offset_lower`; проверки `data_length_lower - offset_lower < chunk` нет, поэтому `memcpy` на 588 пишет за конец буфера, выделенного по первому пакету кадра.
- `rtp.m:631` — `memmove(mp->data + offset_lower, mp->data, mp->len)`.

Уточнение к первоначальной находке: `NDEBUG` в iOS-сборке НЕ определён (`Pods/Target Support Files/toxcore/toxcore.release.xcconfig` даёт только `COCOAPODS=1`), то есть `assert` в бою жив. Это меняет не вывод, а какой из путей срабатывает.

**Сценарий отказа.** Друг, с которым принят и установлен 1:1 звонок, шлёт один lossy-пакет `RTP_TYPE_AUDIO` (без `RTP_LARGE_FRAME`, чтобы не уйти в `handle_video_packet`), `offset_full = data_length_full = 0`, `RTP_HEADER_SIZE` = 80:
- **Один пакет, assert проходит:** длина 1373, `data_length_lower = 1293`, `offset_lower = 1292`, чанк 1292. `assert(1293 >= 1292)` ок, `calloc` на 1293, `memmove` (631) пишет 1292 байта начиная с индекса 1292 → **1291 байт за концом буфера, содержимое полностью атакующего**.
- **Два пакета:** первый `data_length_lower=1000/offset=0/chunk=10`, второй с тем же `sequnum`+`timestamp`, `offset_lower=990/chunk=100` — проходит обе имеющиеся проверки и пишет 90 байт за конец через `memcpy` (588).
- Вариант `data_length_lower = 1` при чанке 1292 упирается в живой `assert` → удалённый `abort` приложения (тоже отказ, но другой).

**Как чинить (по шагам).**
1. Перед `rtp.m:628` добавить проверку из desktop-копии:
   `if ((uint32_t)(header.data_length_lower - header.offset_lower) < (uint32_t)(length - RTP_HEADER_SIZE)) { LOGGER_WARNING(log, "..."); return -1; }`
2. В условие на `rtp.m:580` добавить третий дизъюнкт — **строго после** существующего `session->mp->header.data_length_lower <= header.offset_lower`: `|| session->mp->header.data_length_lower - header.offset_lower < length - RTP_HEADER_SIZE`. Порядок обязателен: при `offset_lower > data_length_lower` беззнаковая разность переполнится вверх и проверка молча пропустит пакет; desktop-порядок правильный, его и сохранять.
3. В `new_message` (`rtp.m:59`) заменить `assert(allocate_len >= data_length)` на `if (allocate_len < data_length) return nullptr;` — иначе остаётся самостоятельный дефект: удалённый `abort` одним пакетом.
4. Проверить, что вызывающий на 628-635 корректно обрабатывает `nullptr` (он уже это делает, ветка `LOGGER_WARNING` + `return -1`).

**Как проверить.** `scripts/check-ios-rtp-reassembly.py:101` сейчас извлекает только `static bool fill_data_into_slot` и legacy-ветку не смотрит вовсе. Расширить гейт на `handle_rtp_packet`/`new_message` и добавить в харнесс три кейса выше (один пакет `1293/1292`, два пакета `1000/990+100`, `data_length_lower=1` + чанк 1292 — все три должны быть отброшены без записи за границы; собрать харнесс под ASan). Легитимный трафик не ломается: отправитель всегда шлёт `offset + chunk <= total`, граничный случай проходит (сравнение строгое).

**Объём.** Небольшой: три правки по 1-3 строки + расширение гейта.

### RR3-03 (medium) — desktop/Android toxcore: единственный `return` без разблокировки `endcall_mutex`

**Что не так.** `khandaq-desktop/buildscripts/toxcore/toxav/rtp.c`: `handle_rtp_packet` захватывает рекурсивный `endcall_mutex` через `pthread_mutex_trylock` (543) и отпускает его на всех выходах — кроме одного. Ранний выход в метке `NEW_MULTIPARTED` (939-944) делает голый `return;`. Проверены все выходы после trylock: 551-554, 566-569, 572-575, 708-711, 724-727, 731-734, 739-742, 747-750, 837-840, 871-874, 900-903, 921-924 и финальный 956 — везде `unlock` есть, только 943 без него. Мьютекс рекурсивный (`util.c:55-63`, `PTHREAD_MUTEX_RECURSIVE`), поэтому счётчик владения у потока `tox_iterate` навсегда остаётся ненулевым. iOS этой ветки не имеет (мьютекс — особенность форка zoff, живущего в desktop/Android).

**Сценарий отказа.** Друг, с которым принят звонок, шлёт один lossy-пакет `RTP_TYPE_AUDIO`: `offset_full = data_length_full = 0`, `offset_lower = 0`, `data_length_lower = 10`, полезная нагрузка 100 байт. `10 != 100` → multipart; `session->mp == nullptr` → `NEW_MULTIPARTED` → условие 939 истинно → `return;` при захваченном мьютексе. (Ещё проще: выставить `RTP_LARGE_FRAME` на аудио-пакете — тогда проверка `offset_lower >= data_length_lower` вообще пропускается и достаточно `data_length_lower = 0`.)
`tox_iterate` крутится в потоке Core (`khandaq-desktop/src/core/core.cpp:383`), а `toxav_call_control` вызывается прямо из GUI-потока (`src/widget/widget.cpp:1185`, `src/widget/form/chatform.cpp:427,440` → `CoreAV::cancelCall`, `coreav.cpp:313-320`) → `call_kill_transmission` → `pthread_mutex_lock(av->toxav_endcall_mutex)` (`toxav.c:687 → 2736`). Блокировка вечная: **виснет GUI-поток целиком** — пользователь не может положить трубку, окно замирает. При выходе `toxav_kill` (`toxav.c:245-247`) делает `lock/unlock/destroy` — `pthread_mutex_destroy` на удерживаемом мьютексе, UB. Звук при этом продолжает идти (`toxav_iterate` этот мьютекс не берёт), что усложняет диагностику.

**Как чинить (по шагам).**
1. `rtp.c:943`: `return;` → `pthread_mutex_unlock(endcall_mutex); return;`. Никаких других локов на этой строке не удерживается — выход становится идентичен остальным двенадцати.
2. Так как Docker-образы десктопа клонируют апстрим заново (см. RR3-01 п.6), правку доставлять applier-скриптом, а не только коммитом в дерево. Тот же applier обслуживает и Android (`circle_scripts/deps.sh`, 4 ABI-блока).
3. Дефект апстримный (`zoff99/c-toxcore @2e7a0675`) — если планируется PR в апстрим, это одна строка.
4. Добавить в `scripts/` простой линтер: каждый `return` в теле `handle_rtp_packet` после строки с `trylock` обязан быть предварён `pthread_mutex_unlock`. Гейт дешёвый и ловит весь класс.

**Как проверить.** Юнит-кейс не нужен: собрать desktop с правкой, во время звонка отправить описанный пакет (или прогнать харнесс с выдернутой функцией) и убедиться, что «Завершить звонок» отрабатывает. Без правки та же последовательность подвешивает GUI намертво.

**Объём.** Небольшой (одна строка + доставка через applier).

### RR3-04 (medium) — `JNI_COMMIT` не освобождает копию: утечка нативной кучи на каждом NGC-аудиокадре

**Что не так.** `khandaq-android-trifa/jni-c-toxcore/jni-c-toxcore.c`, шесть мест: 8473, 8474, 8475 (`y`/`u`/`v` в `toxav_ngc_video_decode`), 8537 и **8589** (`encoded_frame_bytes` в video/audio encode), 8640 (`pcm_decoded`). Режим `JNI_COMMIT` по спецификации копирует содержимое обратно, но НЕ освобождает буфер; освобождает только режим `0`. В ART `GetPrimitiveArray` для перемещаемого массива выделяет копию, а `ReleasePrimitiveArray` делает `delete[]` только под `if (mode != JNI_COMMIT)`. Автор знает правильный режим — в криптомостах Khandaq (4685, 4687, 4750) используется `0` с комментарием «not JNI_ABORT: the generated key has to be copied back».

Практически течёт аудиопуть: `encoded_aframe = new byte[1362]` (`GroupMessageListActivity.java:4966-4967`, `MAX_GC_PACKET_CHUNK_SIZE=1372`) — обычный перемещаемый массив. Видеобуферы (327680/81920/40000/20000 байт) попадают в large-object space, копии нет, поэтому не текут.

Измерено на двух эмуляторах (API 33 и API 36): `is_copy=1` для `byte[1362]`, `is_copy=0` для больших; 300 000 циклов `Get+Release(JNI_COMMIT)` дают RSS +530 МБ (~1.85 КБ на вызов), те же 300 000 с `mode 0` — дельта ровно 0.

**Как чинить (по шагам).**

### RR3-07 (medium) — проверка предка в `release-provenance` падает на shallow-клоне

Автор про эту ловушку знает: в `scripts/record-push-release-evidence.py:188` такая же проверка предварена `git rev-parse --verify` и деградирует до `::warning` с текстом «мелкий клон?», а в других workflow глубина задаётся явно (`changelog.yml:21,39`, `gitleaks.yml:24`, `security-checks.yml:278`, `ios-build.yml:43`). **Сценарий отказа.** `android-native-so.yml` имеет только `workflow_dispatch` — автоматического прогона на релизном коммите не бывает. Самый свежий успешный прогон на master — `31890361557` от 15.08, headSha `241b0a53`; это предок текущего master, но не HEAD. Совет из самого сообщения («run the workflow on the release commit») неисполним: диспатч по тегу даст `headBranch` = имя тега, которое отсекается фильтром `--branch master`.

**Как чинить (по шагам).**
1. Дешёвый и точный вариант: перед циклом добавить `git fetch --no-tags --filter=blob:none origin +refs/heads/master:refs/remotes/origin/master` — тянет только граф коммитов. Альтернатива без локального git: `gh api repos/ummalife/khandaq/compare/$cand_sha...$GITHUB_SHA` и принимать статусы `identical`/`ahead`.
2. Грубый, но рабочий вариант: `with: fetch-depth: 0` для `actions/checkout` в job `build-attest`. Цена — объектная база ~819 МБ на каждый релиз. Остальные git-вызовы job (`git diff --exit-code` на 204 и 227) к глубине безразличны.
3. Без этого любая будущая смена глубины снова превратит гейт в проверку равенства — молча.
4. Отдельно учесть: даже после починки пройдёт только прогон `31890361557`. Если нативный стек будет пересобран на релизном коммите, байты почти наверняка разойдутся с закоммиченными суммами и релиз упадёт на строке 121 — `nativelibs/SHA256SUMS.txt` придётся обновлять тем же PR (это же требование действует для RR3-04).

**Как проверить.** Прогнать job на тестовом теге от текущего master и убедиться, что в логе появляется `native build 31890361557 was made at 241b0a53, which is an ancestor of this release`, а затем `shasum -a 256 -c` проходит. Негативный тест: подсунуть `cand_sha` из ветки, не являющейся предком, — гейт должен отказать по существу, а не по неразрешимости объекта.

**Объём.** Небольшой (1-3 строки + негативный тест).

**Объём.** Небольшой (UI + сигнал + два места в `ProfileInfo`).

### RR3-10 (low) — Android: после смены пароля `savedata.tox` временно остаётся на диске в открытом виде

**Что не так.** `khandaq-android-trifa/.../DbRekeyHelper.java:284-311`: на финализации rekey staged-снимок расшифровывается из Keystore-обёртки и **незашифрованный** файл подставляется на место `savedata.tox` (комментарий 281-284 прямо говорит, что расчёт на «первый `update_savedata_file` после входа»). `savedata.tox` — приватный ключ Tox-профиля; в обычной работе он зашифрован toxencryptsave фразой `Base64(SHA256(dbKey))` (`HelperGeneric.java:3951-3952`, `MainActivity.java:3509-3513`).

Оценка риска уточнена по сравнению с первоначальной: перешифровка не «когда-нибудь», а детерминированно при ближайшем старте tox — `TrifaToxService.tox_thread_start_fg` вызывает `HelperGeneric.update_savedata_file_wrapper()` на строках 1039 и безусловно на 1273, а сам rekey исполняется в том же запуске, который пользователь инициировал ради входа под новым паролем. `allowBackup=false` (`AndroidManifest.xml:114-116`) исключает OEM/облачный бэкап. Для root на живом устройстве дельты нет вовсе: `PREF__DB_secrect_key` лежит в prefs под Keystore-ключом без привязки к аутентификации пользователя, и «правильно зашифрованный» savedata такой атакующий откроет и так. Реальная дельта — ровно один случай: снятый дамп приватного каталога без возможности пользоваться Keystore устройства, снятый в окне между финализацией rekey и ближайшим стартом tox.

Тот же результат даёт осиротевший `savedata.tox.rkplain`, если процесс убьют в миллисекундном окне между экспортом и `finally`.

**Как чинить (по шагам).**
1. **Не использовать предложенные «очевидные» пути — они не работают:**
   - `export_savedata_file_unsecure(passphrase, path)` (`jni-c-toxcore.c:1048-1078`) принимает `passphrase`, но **ни разу его не использует** — всегда пишет сырой `tox_get_savedata`;

2. Добавить JNI-обёртку над `tox_pass_encrypt` (функция уже используется в `jni-c-toxcore.c:943`), принимающую байты и парольную фразу.
3. В `DbRekeyHelper` на финализации: расшифрованный снимок (`sdNew`) перешифровать фразой `sha256(newKey)` (та же формула, что в `MainActivity.savedata_passphrase_for`, `newKey` доступен на строке 328) и только потом переименовывать в `savedata.tox`.
4. Альтернативно/дополнительно — шифровать уже на этапе `stageSavedataSnapshot`, чтобы открытый `.rkplain` не создавался вовсе.
5. В `cleanupCopies` (508) и `abortAndRestore` (355) добавить удаление `sibling(savedata, ".rkplain")`.
6. Подстраховка на входе не нужна: `TrifaToxService` уже безусловно переписывает savedata на строках 1039/1273.

**Как проверить.** Сменить пароль, дождаться финализации rekey, убить процесс до входа, снять `adb shell run-as org.khandaq.messenger cat files/savedata.tox | head -c 16` — первые байты должны быть магией toxencryptsave (`toxEsave`), а не сырым форматом. Плюс убедиться, что `files/savedata.tox.rkplain` отсутствует после аварийного прерывания.

**Объём.** Средний (новая JNI-обёртка + правка финализации).

### RR3-12 (low) — откат сайта публикует конфиги nginx в веб-корне

**Что не так.** `scripts/deploy-site.sh`: снимок сайта хранит копию nginx-конфигов **внутри** дерева — `mkdir -p '$SNAP_ROOT/$STAMP/_nginx'` и копии `khandaq-security-headers.conf` и `site.conf` (255-257). **Сценарий отказа.** Атакующий периодически запрашивает `https://khandaq.org/_nginx/site.conf` — имена публично известны, репозиторий открыт. Рядом лежит `_nginx/khandaq-security-headers.conf`. Утекает топология, не учётные данные, и требуется гонка с редкой ручной операцией — отсюда low.

**Побочный дефект той же строки, более неприятный:** `cp -al` (36) создаёт жёсткие ссылки на файлы снимка, поэтому `chown -R www-data:www-data` (41) меняет владельца тех же инодов внутри `$PREV/_nginx`, а строки 46 и 52 копируют их обратно через `cp -a` (сохраняет владельца). **Как чинить (по шагам).**

3. Подстраховка в конфиге: добавить в managed-регион `infra/nginx/khandaq-static-site.locations.conf` перед `location /` блок `location ~ ^/_ { deny all; }`. Приоритеты nginx это безопасно (`=` и `^~` блоки выигрывают, своих путей с подчёркиванием у сайта нет).
4. Исправить комментарий 55-56, чтобы следующий сопровождающий не воспроизвёл ту же модель («дело не в reload, а в том, что root действует непрерывно»).

**Что проверялось и оказалось НЕ дефектом — не переоткрывать без новых доказательств:**
- Вся линия `khandaq-android/` (aTox, `applicationId ltd.evilcorp.atox`) не собирается, не подписывается и не публикуется; её собственные workflow во вложенном `.github/workflows` GitHub не исполняет. - Вся `infra/bootstrap/` выведена из эксплуатации в 06.2026, DNS нод — NXDOMAIN, ни один workflow её не трогает. Пять кандидатов отклонены (443 без `CAP_NET_BIND_SERVICE`, `deploy-node.sh` с кодом 0, docker-compose без песочницы, фолбэк docker-compose по регистру — последний ещё и фактически неверен: GitHub сопоставляет имена ассетов без учёта регистра, проверено запросом).
- `ByteBuffer.allocateDirect(...).array()` на Android **не бросает**: AOSP-реализация `DirectByteBuffer` держит backing array (`MemoryRef`). Три кандидата, построенных на обратной посылке, отклонены; заодно выяснилось, что комментарий `MainActivity.java:5470` («a direct buffer has no backing array on Android») фактически ошибочен и вводит читателя в заблуждение — его стоит поправить отдельно, вне контекста безопасности.
- Раскладка nginx-конфигов через `/tmp` на боевом хосте блокируется ядром (`fs.protected_symlinks=1`, `fs.protected_regular=2`, у root исключений нет), файлы там лежат `root:root 0644` — заявленного захвата конфигурации не наступает.
- Предложение ужать права `secrets/` до 700/600 отклонено как вредное: контейнер реле работает под uid 10001 и перестал бы читать service account — это буквально воспроизведение инцидента K-05.
