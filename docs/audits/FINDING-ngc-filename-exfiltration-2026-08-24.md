# Имя файла в группе позволяло вытянуть чужой файл из зашифрованного хранилища

**Платформа:** только Android. **Серьёзность:** высокая. **Найдено:** 2026-08-24, при разборе
предупреждений CodeQL (KQ-R9). **Статус:** исправлено до выпуска 0.2.43.

## Что было не так

Имя входящего файла в NGC-группе приходит по сети и выбирается отправителем. На пути к диску оно
проходит через `get_incoming_filetransfer_local_filename()` — тот убирает разделители пути и
нейтрализует `.`/`..`. Для 1:1-передач и для обычных групповых так и происходило.

Но у чанкового группового приёма есть **второе** имя. `resolveDisplayFilename()` читает его прямо из
пакета (`data`, смещение 44) и не фильтрует ничего, кроме пробелов по краям — это «как отправитель
назвал файл», для показа в чате. Проблема в том, что оно записывалось не только в текст сообщения,
но и в `GroupMessage.file_name` — в четырёх местах `HelperGroup.java`.

Сам файл при этом сохранялся по безопасному пути. Опасным было то, что `file_name` — не подпись, его
склеивают с каталогом:

```java
// send_ngch_syncfile: отдаёт историю группы новому участнику
final File f1 = new File(m.path_name + "/" + m.file_name);   // ← сюда попадало ../
...
inputStream.read(file_raw_data);
tox_group_send_custom_private_packet(..., peer_pubkey, ..., data);  // ← и уходило пиру
```

## Как это использовать

1. Атакующий состоит с жертвой в одной NGC-группе и отправляет туда файл чанковой передачей, назвав
   его `../../<путь к нужному файлу>`. Размер объявляет небольшим — так строка не попадёт под отсев
   «слишком большой файл» на шаге 3.
2. У жертвы создаётся запись с этим сырым именем.
3. Атакующий (или его второй аккаунт) запрашивает историю группы. `send_ngch_syncfile` открывает
   `path_name + "/" + file_name`, выходит за каталог группы, читает **другой** файл и отправляет его
   содержимое запросившему. Отсев по размеру считает длину уже того файла, на который указал `..`.

Итог: произвольный файл размером примерно до 40 КБ из зашифрованного хранилища (`IOCipher`) —
вложения из других переписок, аватары — уходит атакующему. Жертва не видит ничего необычного.

Второй путь, тот же корень: при «Сохранить» имя используется и как источник, и как приёмник копии,
поэтому `../` читал файл за пределами каталога чата и писал за пределы каталога экспорта.

## Что исправлено

**Источник.** Все четыре места пишут в `file_name` санитизированное имя (`sanitised_stored_filename`).
Пользователь по-прежнему видит имя, которое выбрал отправитель, — оно остаётся в тексте сообщения.

**Защита в глубину.** Записи, созданные прежними версиями, уже лежат в базах с сырым именем, поэтому
одной правки источника мало. Появился `path_inside_dir_or_null()`, отвергающий склейку, которая
покидает каталог; он стоит там, где содержимое файла уходит наружу: `send_ngch_syncfile`, обе функции
экспорта, сборка пути для проигрывания медиа.

**Регрессия.** `scripts/check-incoming-filename-sanitizer.py` (в CI): проверяет сам санитайзер, то,
что каждый путь приёма через него проходит, что ни одна запись не хранит сырое имя, и что обе
отдающие наружу функции делают проверку пути. Проверен мутациями — снятие любой из трёх защит роняет
его.

## На iOS этого нет

Там `displayFilename` хранится отдельно от пути (`filePath` — безопасный), склейки каталога с именем
от пира в коде нет, и файлы при синхронизации истории iOS не раздаёт вовсе, так что и вектора нет.

## Замечание о том, как это нашлось

CodeQL пометил 16 мест как `java/path-injection`, и все шестнадцать — ложные: они указывали на
исходящие передачи и на пути, где имя уже отфильтровано. Настоящая дыра была в месте, которое
сканер **не** пометил. Отсюда практический вывод для KQ-R9: ценность была не в списке предупреждений,
а в том, что их разбор заставил пройти все пути имени файла целиком.
